# M4 发布 v0.1.0 实施计划

> **给执行者：** 在当前会话里按顺序执行（executing-plans）。步骤用复选框（`- [ ]`）跟踪。

**目标：** 由 CI 构建并发布 v0.1.0：NSIS 安装包和免安装 exe，附 `SHA256SUMS` 和构建来源证明，`gh attestation verify` 核对通过（设计文档第 12、13 节）。

**做法：** `release.yml` 在推送 `v*` tag 时，在 Windows 上用 tauri-cli 构建，生成哈希和构建来源证明，再由一个单独的 job 创建 GitHub Release。手动运行时只构建、上传构建产物，用来在打 tag 之前试跑。README 改写成面向使用者的说明。

**技术栈：** tauri-cli 2.12.0（NSIS 打包）、GitHub Actions（`actions/attest-build-provenance`）、GitHub CLI。

**开始前已经定下的事（2026-10-13、10-14 和用户确认）：**
- v1 不写日志文件（设计文档第 8 节，提交 ed08d3a）。
- 安装包只为当前用户安装，不需要管理员权限，程序装在 `%LOCALAPPDATA%\MhyCarry\`。
- 因此数据目录改为 `%LOCALAPPDATA%\io.github.shulkx.mhycarry\`，即 Tauri 的应用标识，这是 Tauri 应用的标准做法。卸载时勾选“删除应用程序数据”会删掉它（设计文档第 4、8 节，提交 a5b695d）。
- tauri-cli 用 2.12.0，不用最新的 2.12.2：2.12.2 发布才几天，2.12.0 已经发布两周以上，和锁定的 tauri 2.12.3 同属 2.12。
- 第三方 Action 都固定到 commit SHA，选发布两周以上的版本：
  - `actions/attest-build-provenance` v4.2.2：`4d101475d8b20a2381f78447822ac1eab6504dd8`
  - `actions/upload-artifact` v7.0.1：`043fb46d1a93c77aae656e7c1c64a875d1fc6a0a`
  - `actions/download-artifact` v8.0.1：`3e5f45b2cfb9172054b4087a40e8e0b5a5461e7c`
  - `actions/checkout` v7.0.1 和 `ci.yml` 相同。

### 任务 3：`release.yml`

**文件：** 新建 `.github/workflows/release.yml`（完整内容见仓库里的文件）

要点：
- 触发：推送 `v*` tag；或手动运行（workflow_dispatch），只构建、上传构建产物，不生成证明也不发布。
- `build` job（windows-latest）：
  - 权限 `contents: read`、`id-token: write`、`attestations: write`；
  - checkout 设 `persist-credentials: false`，不用 rust-cache；
  - 打 tag 时核对 tag 和 `tauri.conf.json` 的版本号一致；
  - `cargo tauri build --bundles nsis --ci`；
  - 把安装包和 `mhy-carry.exe` 复制到 `dist/`，改名为 `MhyCarry_<版本>_x64-setup.exe`、`MhyCarry_<版本>_x64-portable.exe`；
  - 生成 LF 换行的 `SHA256SUMS`；
  - 打 tag 时用 `attest-build-provenance` 给 `dist/*` 生成证明；
  - 上传构建产物 `dist`。
- `release` job（ubuntu-latest，只在打 tag 时运行）：
  - 只有它有 `contents: write`；
  - 下载 `dist`，用 `sha256sum -c` 核对；
  - 先建草稿 Release、传文件，再正式发布。仓库开启了不可变发布。
