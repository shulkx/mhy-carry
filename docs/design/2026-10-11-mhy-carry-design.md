## 1. 背景与目标

MhyCarry 识别屏幕上的米哈游游戏登录二维码，用你绑定的账号确认登录，扫码前不用掏出手机。常见用法是让朋友或主播帮你打难关：对方的游戏客户端显示登录二维码，你在自己电脑上用 MhyCarry 扫码，把账号登录到对方那里。

同类工具 MHY_Scanner 的 Release 安装包不是由 CI 从公开源码构建的，也无法和源码对照验证。作者在 issue #182（2026-06-01）里说明，新版源码不会公开，只给内部贡献者。程序启动时还会访问一个归属不明的第三方服务器。MhyCarry 的出发点就是**可验证、不经过第三方**：
- 账号凭证只发给米哈游官方域名；
- 发布的程序只由 CI 从公开源码构建，并附构建来源证明；
- 依赖尽量少，代码容易审查。

## 2. 范围

**v1 包含：**
- 用米游社 App 扫码绑定一个账号，可以解绑。
- 扫描三种截图目标里的原神客户端登录二维码：自动识别的游戏窗口、手动指定的窗口（比如浏览器里正在看的直播）、整个显示器。
- 每次登录前都弹出系统原生对话框，由你确认。
- 只发布 Windows 版，包括安装包和免安装 exe。

**v0.2 增加（2026-10-14 和用户确认，第 6.4 节）：**
- 多账号：可以绑定多个账号，选一个“使用中”的账号扫码登录。
- 显示每个账号的原神角色昵称、等级和游戏 UID，可以给账号写备注。
- 直播流抢码放到 v0.3，单独设计。

**v1 不包含：**
- 加密存储（明文存储，见第 8 节；v0.2 也不加密，用户确认）、托盘图标、自动更新。多账号在 v0.2 加上。
- 其他游戏、直播流抢码、macOS 和 Linux 版。
- 短信登录、Cookie 登录、密码登录。

**以后的扩展**都已经在架构里留好了位置（第 5 节）：
- 其他游戏：加一条游戏配置。
- 直播流抢码：加一个画面来源和一种确认策略。
- 加密存储：换一个存储实现。
- macOS 和 Linux：加对应平台的截图实现。
- 云原神：它的登录二维码是 passport 网页登录码（`user.mihoyo.com/login-platform/...`），不是客户端的 `qr_code_in_game.html`。这种二维码本身看不出是哪个游戏，要先调 `scanQRLogin`，再按返回的 `app_id` 核对。v1 不支持。

## 4. 仓库结构

仓库目录 `E:\GitHub\mhy-carry`，GitHub 仓库名 `shulkx/mhy-carry`。

```
mhy-carry/
├─ Cargo.toml              workspace
├─ rust-toolchain.toml
├─ deny.toml               cargo-deny 配置
├─ crates/
│  ├─ core/                mhy-carry-core：纯逻辑，不访问网络，不调用操作系统 API
│  ├─ api/                 mhy-carry-api：米哈游接口客户端
│  ├─ platform/            mhy-carry-platform：窗口枚举、截图、数据目录
│  ├─ runner/              mhy-carry-runner：扫码会话的运行循环，cli 和 app 共用
│  └─ cli/                 mhy-carry-cli：命令行工具，用来验证协议和调试
├─ app/
│  ├─ src-tauri/           mhy-carry：Tauri 应用（Rust 端）
│  └─ ui/                  index.html、main.js、style.css
├─ docs/
└─ .github/workflows/      ci.yml、release.yml
```

依赖关系是单向的：`app`、`cli` 依赖 `runner`、`api`、`platform`；`runner` 依赖 `api` 和 `core`；`api`、`platform` 再依赖 `core`。`core` 不依赖其他任何单元，也不依赖任何平台相关的库。

命名约定：
- 仓库、目录和 Cargo 包名用小写加连字符（`mhy-carry-core`）。
- 给人看的名字用 `MhyCarry`：窗口标题、安装包、安装目录、README 标题。
- Tauri identifier 用 `io.github.shulkx.mhycarry`，数据目录也用这个名字（第 8 节）。

## 5. 核心接口（扩展点）

下面的接口都定义在 `core` 里，签名只是示意，实现时以代码为准。

**`FrameSource`（画面来源）：** 提供一帧帧画面，并说明画面来自哪里。

```rust
pub trait FrameSource {
    fn next_frame(&mut self) -> Result<Frame, CaptureError>;
    fn describe(&self) -> SourceInfo;
}
pub struct Frame { pub width: u32, pub height: u32, pub luma: Vec<u8> } // 灰度图
pub enum SourceKind { GameWindow, PickedWindow, Monitor /* 以后：LiveStream */ }
pub struct SourceInfo { pub kind: SourceKind, pub label: String } // 如 "YuanShen.exe（原神）"
```
- **v1 的实现**（在 `platform` 里）：游戏窗口、指定窗口、显示器三种。
- **以后：** 直播流（新增 `live` crate，调用 ffmpeg 子进程）、macOS 和 Linux 截图。

**`QrDecoder`（二维码识别）：** 从一帧里识别出所有二维码的文本。v1 用 rxing 实现。

**`GameProfile`（游戏配置）：** 一张静态配置表，每个游戏一条记录。

```rust
pub struct GameProfile {
    pub display_name: &'static str,    // "原神"
    pub app_id: u32,                   // 4
    pub biz_key: &'static str,         // "hk4e_cn"，也是 panda 扫码接口路径里的那一段
    pub passport_app_id: &'static str, // "c76ync6mutq8"，scanQRLogin 返回的应用 ID
    pub process_names: &'static [&'static str], // ["YuanShen.exe"]
}
```
- 支持新游戏时只需要加一条配置。
- 接口地址不放在配置里，由 `api` 按 `{panda 域名}/{biz_key}/combo/panda/qrcode/scan` 拼出来。各游戏的路径规律相同，而且这样测试时才能把域名换成本地假服务器。

**`ConfirmPolicy`（确认策略）：** 识别到合法的二维码后决定怎么做，结果是 `AskUser`（问你）、`AutoConfirm`（直接登录）或 `Ignore`（忽略）。
- v1 只有 `AlwaysAsk`：每次都问你。
- 以后的直播抢码模式加 `AutoConfirmOnce`：你手动开启后，自动确认一次就关闭。
- 硬性规则：画面来源是 `PickedWindow` 或 `Monitor` 时**永远不会**自动确认。策略如果返回 `AutoConfirm`，`ScanSession` 会强制改成 `AskUser`。这条规则写在 `core` 里，任何策略都绕不开。

**`LoginApi`（登录接口）：** 检查凭证、扫码登录的三步请求（第 6.2 节），以及绑定账号相关的请求。
- 正式实现在 `api` 里。
- 测试时用假实现。
- 以后接入登录方式不同的服务器（比如崩坏3 B服）时，再加一个实现。

**`AccountStore`（账号存储）：** 读写账号文件。
- v1 的 `JsonFileStore` 放在 `core`，只用标准库读写文件，文件路径由调用方传入。
- 以后的加密存储是另一个实现。

**`ScanSession`（扫码会话状态机）：** 纯状态机，不包含线程，也不做任何 I/O。调用方把事件喂给它，比如“识别到二维码”“用户的选择”“接口返回结果”“超时”，它返回下一步该做什么，比如“弹窗询问”“调用 scan/confirm”“停止”。截图、识别和网络请求都由 `app` 或 `cli` 的运行循环负责，所以状态机可以单独测试。它同时产出第 6.3 节里扫描会话那一块的快照；账号和绑定流程不归它管，由 `app` 或 `cli` 维护。

## 6. 主要流程

### 6.1 绑定账号（用米游社 App 扫码）

1. 你点“绑定账号”，`api` 向米哈游申请登录二维码，Rust 端生成 SVG 交给界面显示。
2. 你用米游社 App 扫码并在手机上确认。程序每 1–2 秒查询一次状态，界面依次显示“等待扫码 / 已扫码，请在手机上确认 / 绑定成功”。
3. 确认后拿到 uid、mid、stoken，写入账号文件。
4. 二维码过期就提示刷新。
   - v0.2 起，绑定的通行证 ID 不在列表里就添加为新账号；已经在列表里就只更新它的凭证，备注不变。不管哪种，绑定成功的账号都设为“使用中”。添加账号不会替换别的账号，所以不再需要确认。
   - 绑定成功后查一次原神角色（第 6.4 节）。
   - v0.1 只支持一个账号，再绑定时先确认，再替换掉旧账号。

接口（2026-10 对照活跃开源项目核对，来源见第 16 节）：

1. `POST https://passport-api.mihoyo.com/account/ma-cn-passport/app/createQRLogin`，请求体 `{}`，返回 `data.url`（给米游社扫的二维码内容）和 `data.ticket`。
2. 轮询 `POST .../app/queryQRLoginStatus`，请求体 `{"ticket": …}`。
   - `data.status` 依次变为 `Created`、`Scanned`、`Confirmed`。
   - 确认后，`data.tokens` 里 `token_type == 1` 的那一项就是 v2 stoken，`data.user_info` 里有 `aid`（即 uid）和 `mid`。
   - retcode `-3501` 表示二维码过期，`-3505` 表示用户在手机上取消。
3. 请求头用米哈游启动器（HoYoPlay）的那一套：`x-rpc-app_id: ddxf5dufpuyo`、`x-rpc-client_type: 3`、`x-rpc-device_id`、`User-Agent: HYPContainer/1.1.4.133`。不需要 DS 签名。

MHY_Scanner 公开源码里的旧方案（panda `fetch`/`query`，再调 `getTokenByGameToken` 换 stoken）从 2026-05 底起会返回 `-5300`，已经不能用。

### 6.2 扫码登录

1. **选择截图目标：**
   - **自动**（默认）：按 `GameProfile.process_names` 找游戏窗口。找不到时显示“等待原神窗口…”，每 2 秒重找一次。扫描中游戏窗口关了，就回到等待，因为游戏可能会重开。只在原神是最前面的窗口时扫描，不在最前面时暂停，并显示“原神不在最前面，切回游戏后继续”：截的是游戏窗口所在的屏幕区域（第 14 节），游戏不在最前面时可能截到盖在上面的窗口，比如正在播放别人二维码的浏览器小窗，二维码的来源就会说错。
   - **指定窗口**：从可见窗口列表（标题 + 进程名）里选一个。列表里没有太小的窗口（宽或高不到 200 物理像素，比如输入法状态栏）和本程序自己的窗口；游戏窗口排在最前面，默认选中。窗口移动后截图区域跟着移动；窗口最小化时暂停，并显示“窗口已最小化”。窗口关了就停止扫描。
   - **显示器**：从显示器列表里选一个，默认主显示器。显示器断开就停止扫描。
2. **截图和识别：**
   - 每秒最多 4 帧。
   - 识别在单独的线程里进行；识别跟不上时直接丢帧，只处理最新的一帧。
   - 一帧里有多个二维码时逐个校验。合法的登录码不止一个（ticket 不同）时不弹窗，提示“画面里有多个登录二维码，无法确定要登录哪一个”，然后继续扫描。直播画面里可能有别人故意放上去的码，确认框里的文字分辨不出是哪一个。
   - 等你确认和登录期间暂停识别，结束后再继续。同一时间最多只有一个确认框。
3. **校验**：对二维码文本执行第 7 节的规则，不合格的直接忽略，不打扰你。
4. **去重**：同一个 ticket 在本次会话里只处理一次，你拒绝过的也不再弹窗。
5. **确认**：由 Rust 端调用 Windows 的 `MessageBoxW` 弹出系统确认框，例如：

   > 在 YuanShen.exe（原神）中发现**原神**登录二维码。
   > 用账号「大号」（原神 UID 100000001，通行证 300012345）登录？确认后，显示这个二维码的设备将登录你的账号。

   扫描用的是“使用中”的账号（第 6.4 节），扫描中不能切换。还没查到原神角色时省掉原神 UID；账号既没有备注也没查到角色时，写成“用通行证 300099999 的账号登录？”。
   > [确定] [取消]（默认按钮是“取消”）

   - **置顶，并尝试切到前台。** 自动模式下发现二维码时，游戏一定在最前面（第 1 步），确认框不置顶就会被游戏挡住。
   - **按钮是“确定 / 取消”，默认“取消”。** 你在游戏里按着键盘时确认框突然弹出，误按回车、空格或 Esc 只会取消；两个按钮都没有快捷字母，按字母键也不会确认（“是(Y) / 否(N)”单按 Y 就会确认，M3 审查时改掉了）。系统不让它抢到焦点时，按键仍然进游戏。只能用鼠标点“确定”。
   - **同时闪任务栏、响提示音**，万一没看到还有提醒。原神如果用的是独占全屏，任何窗口都盖不住它，这时只能靠这两项。M3 实测没有测全屏模式，以后再确认（第 14 节第 5 项）。
   - 解绑也用同样的系统确认框（第 9 节）。
   - `cli` 里没有图形界面，同样的内容改为在终端里提问，输入 y 确认。
   - 游戏名取自程序自己的 `GameProfile`，不用二维码里的 `app_name` 文字。
   - 来源描述取自 `SourceInfo`。
   - 账号名称和 ID 都完整显示，不打码：账号是用户自己的，需要一眼认出用的是哪个账号。
6. **登录**：你点了“登录”，程序才依次调用下面三步。所有请求都带 `x-rpc-app_id: bll8iq97cem8` 和 `x-rpc-device_id`，不带 DS 签名。
   1. **panda 扫码：** `POST https://api-sdk.mihoyo.com/{biz_key}/combo/panda/qrcode/scan`，请求体 `{"passport_app_id": "bll8iq97cem8", "ticket": …, "app_id": 4, "device": …, "ts": <Unix 秒>}`，`app_id` 是 JSON 整数。返回的 `data.passport_qr_url` 形如 `https://user.mihoyo.com/login-platform/mobile.html?expire=…&tk=…&token_types=1#/login/qr`，按第 7 节末尾的规则校验后，取出 `tk` 和 `token_types`。
   2. **passport 扫码：** `POST https://passport-api.mihoyo.com/account/ma-cn-passport/app/scanQRLogin`，请求体 `{"ticket": <tk>, "token_types": ["1"]}`，用 Cookie `stoken=…;mid=…` 认证。返回的 `data.app_id` 必须等于 `GameProfile.passport_app_id`，否则说明这不是这个游戏的登录码，**取消登录**，不调第 3 步。
   3. **确认：** `POST .../app/confirmQRLogin`，请求体和 Cookie 同第 2 步。

   每一步都要求 `retcode == 0`。已知错误码：`-100` 登录状态失效，`-3501` 二维码过期。
7. **结束**：
   - 登录成功后停止扫描，界面显示结果。
   - 任何一步失败都显示原因（第 10 节）。**只有凭证失效才停止扫描。** 其他失败，包括二维码过期或已被使用、应用不符、网络错误、未知错误码，都只影响当前这个二维码：提示原因后继续扫描，等游戏刷新二维码。
   - 登录请求发出后你要求停止：等登录结果出来再停。登录成功就显示成功，免得账号其实已经登录了却显示“手动停止”。
8. **超时停止**：连续一段时间没发现合法的登录二维码就自动停止扫描，默认 300 秒，可以在设置里改。从开始扫描或画面里上一次出现新的合法登录码时算起，一直留在画面上的旧码不算；等窗口、暂停的时间也算在内。

另外：
- **会话开始时先检查凭证。** 扫描开始前先调 `GET https://passport-api.mihoyo.com/account/auth/api/getCookieAccountInfoBySToken`（Cookie 认证），凭证失效就立刻提示重新绑定，免得扫到码才发现用不了。v0.2 起顺便刷新这个账号的原神角色（第 6.4 节）。
- **旧流程已经不能用。** MHY_Scanner 公开源码里“换 game_token 后调 panda `confirm`”的做法，2026 年起已被各活跃项目弃用。
- **以后的直播抢码模式顺序相反。** 识别到二维码立刻 scan + confirm，因为 scan 要抢在别人前面。这个顺序由 `ConfirmPolicy` 和 `ScanSession` 决定，运行循环本身不用改。

### 6.3 界面状态

Rust 端维护一份完整的界面状态（`AppState`），分账号、绑定流程、扫描会话、设置四块。任何一块有变化，都通过事件 `state-changed` 推送**完整快照**；`get_state` 返回同样的结构。界面只按最新一份快照显示，自己不记状态；漏收事件或者页面重新加载后，再取一次快照就能恢复。快照里永远没有 stoken、ticket、二维码内容和截到的画面。

**账号**

| 状态 | 界面显示 |
|---|---|
| 未绑定 | 还没有绑定账号；[绑定] |
| 有账号 | 使用中的账号卡片；有两个以上账号时显示 [切换账号 (n)]；始终有 [+ 添加账号]。卡片的“⋯”菜单里是编辑备注、重新绑定、解绑 |
| 账号文件格式比本程序新 | 说明情况；绑定、解绑都不可用，因为这种文件只读（第 8 节） |

- 每个账号的凭证状态分未检查、有效、已失效三种，各自独立。已失效的账号卡片变红，“⋯”菜单里“重新绑定”排在第一项。
- 账号文件损坏时，程序已经把它改名备份了（第 8 节），按未绑定处理，并显示一次原因。
- 始终显示凭证明文保存的位置。有残留备份时，显示“删除旧账号文件”按钮，并加一句提示，因为备份里可能有明文凭证。v0.2 起残留备份不再跟着解绑一起删。
- 凭证和原神角色只在开始扫描（以及绑定成功）时查，打开程序时不联网。

**绑定流程**

空闲 → 获取二维码中 → 等待扫码（显示二维码）→ 已扫码，请在手机上确认 → 结束。

- 结束有四种结果：绑定成功（账号变为已绑定）、二维码已过期（可以刷新）、已在手机上取消、失败（显示原因）。绑定成功的提示 5 秒后自动收起（账号已经显示出来了）；其他三种结果一直显示，直到再次绑定或点关闭。
- 绑定和扫描不能同时进行：扫描时不能绑定，绑定时不能开始扫描。

**扫描会话**（由 `ScanSession` 产出，规则见第 6.2 节）

| 状态 | 界面显示 | 说明 |
|---|---|---|
| 空闲 | 未在扫描；显示上次结束的原因 | |
| 检查凭证 | 检查账号凭证… | 每次开始扫描时先查一次 |
| 等待窗口 | 等待原神窗口… | 只有自动模式有 |
| 暂停 | 窗口已最小化，恢复后继续 | |
| 游戏不在最前面 | 原神不在最前面，切回游戏后继续 | 只有自动模式有 |
| 扫描中 | 正在扫描 YuanShen.exe（原神） | 附带最近一条提示 |
| 等你确认 | 请在弹出的对话框里确认（显示游戏、来源、账号名称和 ID） | 这期间暂停识别 |
| 登录中 | 正在登录… | 这期间暂停识别 |

结束原因（结束后回到空闲状态并显示）：
- 登录成功（显示游戏名）；
- 你手动停止；
- 连续 300 秒（按设置）没发现登录二维码；
- 账号凭证已失效，请重新绑定（只把扫描用的账号标为“已失效”）；
- 指定的窗口已关闭，或指定的显示器已断开；
- 截图连续失败 10 次，或者检查凭证时出错（比如断网），并显示具体原因。

最近一条提示（带时间，扫描不中断）：
- 画面里有多个登录二维码，无法确定要登录哪一个；
- 二维码已过期或已被使用，等游戏刷新；
- 服务器说这是“××”的登录码，不是原神，已取消；
- 你取消了这次登录，同一个码不会再问；
- 登录失败，并显示原因（网络错误、未知错误码等）。

**命令行**：`cli watch` 没有图形界面，用同样的扫描会话状态：状态变化时打印一行（带时间），出现新提示时也打印一行；到了“等你确认”就在终端里问 y/N，同时响一声终端提示音，因为终端可能被游戏挡住；按 Ctrl+C 等于手动停止。

**确认框：** 被全屏游戏挡住的问题，用置顶的系统确认框解决，见第 6.2 节第 5 步。

**页面布局**（2026-10-13 和用户确认，可点击的原型见 [ui-prototype.html](ui-prototype.html)）：
- 一个约 440×640 的窗口，单页、不分标签，从上到下三块：
  1. **账号**（v0.2，2026-10-14 和用户确认，原型见 [ui-prototype-accounts.html](ui-prototype-accounts.html)）：
     - 未绑定时是“用米游社扫码绑定”按钮。
     - 有账号时只显示一张“使用中”的账号卡片，账号再多，这一块的高度也不变：
       - 左边是圆形头像，显示名称的首字；没有名称时显示 #。
       - 中间从上往下是名称加 `Lv.60` 小标签；名称用的是备注时，下面补一行“原神昵称 旅行者”；再下面是两个 ID 小标签：`原神 UID | 100000001`、`通行证 | 300012345`。没查到原神角色时，第一个小标签写“未查到”。
       - 右上角是凭证状态（带色点的文字）和“⋯”菜单。菜单里是编辑备注（在卡片里直接改，回车保存，Esc 取消）、重新绑定、解绑，都作用于使用中的账号。
     - 标题行右边是“切换账号 (n) ▼”（两个以上账号时才有）和“+ 添加账号”。切换列表的每行是头像、名称、等级、凭证状态，下面一行小字是原神 UID（没查到时是通行证 ID）；最多显示约 5 行，更多的在列表里滚动。点一行就切换过去。要编辑或解绑别的账号，先切换过去。
     - 绑定中，二维码面板临时替换掉卡片，带“取消”，过期时带“刷新”。重新绑定时多一句“请先在米游社 App 里登录通行证 300067890，再扫码”。
  2. **扫描**：截图目标用“自动 | 指定窗口 | 显示器”三段切换，选后两项时出现下拉列表和“刷新”按钮。一个大按钮“开始扫描”，扫描中变成“停止”，登录中不能点。下面一行大字是当前状态，前面的圆点用颜色区分：灰色是空闲，蓝色是扫描中，黄色是等待或暂停，绿色是成功，红色是出错。再下面一行小字是最近一条提示和时间。大按钮写着扫描用的账号，比如“开始扫描（大号）”。扫描中不能切换目标，也不能切换、添加、编辑或解绑账号。
  3. **设置**（默认折叠）：默认截图目标、多少秒没发现二维码就自动停止（最少 30）。
- 底部一行小字写凭证明文保存的位置，有残留备份时加一句提示。
- 跟随 Windows 的浅色、深色主题；用系统字体（Microsoft YaHei UI），不引用任何外部资源；除了扫描中圆点的闪烁，不加动画。
- 窗口不置顶。v1 没有托盘，扫描中关窗口就是停止扫描并退出。

### 6.4 多账号和原神角色（v0.2）

2026-10-14 和用户逐段确认。

**账号列表**
- 账号文件里可以有多个账号，按绑定的先后排列（第 8 节）。
- **“使用中”的账号**：扫码登录用它。记在 `settings.json` 里（只记本地 ID，不是凭证）；记的账号不存在了，就改用列表里的第一个。扫描中不能切换。
- **添加和重新绑定**是同一个流程（第 6.1 节）：扫码时在米游社 App 里登录的是哪个账号，就添加或更新哪个。
- **解绑**只删一个账号，先用系统确认框问你，框里写明账号名称和通行证 ID。解绑的是使用中的账号时，改用列表里的第一个。
- **残留备份**（`accounts.json.bak-*`）用单独的“删除旧账号文件”删除，不跟着解绑。
- **备注**：可选，最多 20 个字，显示前用 `printable` 清理。
- **账号名称**按“备注 → 原神昵称 → 通行证 ID”取第一个有值的。

**原神角色**
- 程序里的 uid 是**米哈游通行证 ID**，不是原神里的 UID。为了让账号好认，v0.2 用凭证查这个通行证下的原神角色，拿到昵称、等级和游戏 UID。
- 两步请求，都在白名单里已有的 `passport-api.mihoyo.com` 上，都不需要 DS 签名：
  1. `GET /account/auth/api/getCookieAccountInfoBySToken`：就是检查凭证用的接口，Cookie `stoken=…;mid=…`。返回的 `data.cookie_token` 留给第 2 步用。
  2. `GET /binding/api/getUserGameRolesByCookieToken?game_biz=hk4e_cn`，Cookie `account_id=<通行证 ID>; cookie_token=<第 1 步的值>`。返回 `data.list`，每一项有 `game_biz`、`region`、`game_uid`、`nickname`、`level`。
- 只取官服（`region == "cn_gf01"`）的角色；同一个通行证在官服有多个角色时，取等级最高的。
- **什么时候查**：绑定成功后查一次；每次开始扫描、检查凭证时顺便刷新。结果存进账号文件（第 8 节），这些不是凭证。
- **查失败了**：第 2 步失败（接口变化、网络错误、没有官服角色）不算错误，不提示，保留上次存下的结果，登录照常。第 1 步失败照原来的规则处理，比如凭证失效就停止扫描。
- **安全**：`cookie_token` 也是凭证，只在内存里用，不保存、不显示、不写日志；Cookie 请求头标记为敏感，错误信息去掉 URL。白名单不变。
- **核对来源**：Starward 用的就是第 2 步这个接口，只带 Cookie、不带 DS（第 16 节）。另一个常见做法是 `api-takumi` 上的 `getUserGameRolesByStoken`，要 DS 签名和设备指纹，不用。
- **实测**：2026-10-14 用真实账号确认能查到角色（第 14 节第 7 项）。

**命令行**
- `account`：列出所有账号，标出使用中的那个，显示名称、原神角色、通行证 ID 和绑定日期。不联网；凭证状态要用 `--refresh` 查。
- `account --refresh`：逐个检查凭证、查原神角色。
- `account --use <通行证ID>`、`account --note <通行证ID> <备注>`、`account --remove <通行证ID>`、`account --remove-leftovers`。
- `bind`：添加账号，已有的账号只更新凭证。
- `watch --account <通行证ID>`：可选，不写就用使用中的账号。

## 7. 二维码校验规则

二维码文本必须同时满足下面所有条件，否则忽略：

1. 能解析成 URL，scheme 是 `https`，host **正好是** `user.mihoyo.com`（不接受子域名，也不接受相似域名），path 是 `/qr_code_in_game.html`。
2. 带有 `app_id`、`biz_key`、`ticket`、`expire` 这几个参数，而且每个参数只出现一次。
3. `app_id` 和 `biz_key` 必须同时对上 `GameProfile` 表里的同一条记录。v1 只有原神：`app_id=4`、`biz_key=hk4e_cn`。
4. `ticket` 只包含字母和数字，长度在 16 到 64 之间。目前见到的都是 24 位十六进制。
5. `expire` 是 Unix 秒，并且晚于当前时间减 60 秒。允许 60 秒误差，是为了照顾本机时钟不准。

其他参数（`app_name`、`bbs` 等）忽略，界面上也不显示。

原神客户端二维码的样例格式：
`https://user.mihoyo.com/qr_code_in_game.html?app_id=4&app_name=%E5%8E%9F%E7%A5%9E&bbs=true&biz_key=hk4e_cn&expire=1690964505&ticket=<24位十六进制>`

panda 扫码返回的 `passport_qr_url` 来自服务器，同样要校验：https、host 正好是 `user.mihoyo.com`、path 是 `/login-platform/mobile.html`；`tk` 和 `token_types` 各出现一次，`tk` 只含字母、数字和 `-`，`token_types` 是逗号分隔的数字。

## 8. 数据存储（v1 明文）

数据目录是 `%LOCALAPPDATA%\io.github.shulkx.mhycarry\`，文件夹名就是 Tauri 的应用标识（第 4 节）。
- 这是 Tauri 应用的标准做法：WebView2 的缓存也在这里，所有数据只有这一个文件夹。卸载时勾选“删除应用程序数据”，会删掉整个文件夹，包括明文凭证。
- 不叫 `MhyCarry`：安装包只为当前用户安装时，程序装在 `%LOCALAPPDATA%\MhyCarry\`。这是 Tauri 安装包的默认位置，目前改不了（tauri-apps/tauri#7853）。
- 不放在程序目录，免得用户打包分享程序时把账号一起发出去。
- 用 `Local` 不用 `Roaming`，免得在域环境里账号随漫游配置文件同步到服务器。

`accounts.json` 存账号凭证，**明文**。v0.2 起是格式 2：

```json
{
  "format": 2,
  "encryption": "none",
  "accounts": [
    {
      "id": "本地生成的 UUID",
      "uid": "300012345",
      "mid": "…",
      "stoken": "…",
      "note": "大号",
      "bound_at": "2026-10-11T08:00:00Z",
      "game_role": { "nickname": "旅行者", "level": 60, "game_uid": "100000001" }
    }
  ]
}
```

- `uid` 是米哈游通行证 ID。`game_role` 是查到的原神官服角色（第 6.4 节），还没查到时是 `null`。
- 格式 1 只比格式 2 少了 `game_role`。v0.2 能读格式 1 的文件，第一次写入时升级成格式 2。
- 升级格式是为了防止退回旧版时丢数据：v0.1 遇到格式 2 只读不写（见下面的读写规则），不会把多账号文件覆盖成只剩一个账号。

`settings.json` 存设置，不含任何凭证，分享出去也没关系：

```json
{
  "format": 1,
  "device_id": "UUID v4，首次运行时生成，之后固定不变",
  "active_account": "使用中的账号的本地 ID（v0.2 起）",
  "scan": { "default_target": "auto", "idle_timeout_secs": 300 }
}
```

v1 不写日志文件：出错原因和错误码直接显示在界面上和命令行里。多一个日志文件就多一个可能漏出凭证的地方，等以后真需要排查问题时再加，到时遵守第 9 节“日志和错误信息”的规则。

读写规则：
- **原子写入。** 先在同目录写临时文件，刷到磁盘后再替换原文件。
- **文件损坏时不覆盖。** 解析失败时把原文件改名为 `accounts.json.bak-<时间戳>`，提示你重新绑定。这些备份里可能有明文凭证，查看账号时会列出来，解绑时一并删除。
- **遇到更新的格式时只读不写。** `format` 大于程序支持的版本，或者 `encryption` 是不认识的值，程序拒绝写入，并提示“账号文件来自更新的版本”。
- **为加密预留了字段。** 以后加密时，`format` 和 `encryption` 字段让新版程序能识别 v1 的明文文件，并自动迁移成加密格式。
- **明确告知。** README 和界面里写明 token 存在哪里、是明文、怎么删除（解绑，或者直接删掉文件）。

## 9. 安全设计

### 防护目标

| 风险 | 对策 |
|---|---|
| 凭证被发到第三方 | 网络白名单，没有遥测，不连任何第三方服务器 |
| 被诱导把账号登录到别人的设备上（二维码劫持） | 严格校验二维码（第 7 节）；每次都要你确认；弹窗写明二维码来自哪里；自动确认永远不对“指定窗口”和“显示器”开放；确认前核对服务器返回的应用 ID |
| 发布的 exe 被替换，或者和源码对不上 | 只由 CI 构建，附构建来源证明和 SHA256，开启不可变发布 |
| 依赖被投毒 | 依赖尽量少，`Cargo.lock` 锁定版本，cargo-deny 检查，GitHub Actions 引用固定到 commit SHA |

**v1 防不了的：**
- **账号文件泄露。** 文件被人拷走、被同步进网盘，或者电脑中了木马，token 都会泄露，因为是明文。这是 v1 的已知限制，README 会写明。
- **扫整个屏幕时程序能看到屏幕上的所有内容。** 画面只在内存里识别，不存盘、不上传，程序只使用识别出的二维码文本。

### 网络
- HTTP 客户端只能访问白名单域名，发请求前先检查 host。只允许 HTTPS，禁止重定向（`redirect::Policy::none()`），超时 10 秒。
- 白名单只有两个域名：`api-sdk.mihoyo.com`（panda 扫码）和 `passport-api.mihoyo.com`（绑定、检查凭证、passport 扫码和确认）。M1 已实测这两个域名可用（第 14 节）。
- 证书校验用 reqwest 0.13 的默认行为（rustls + 系统证书库），不提供“忽略证书错误”之类的选项。
- 测试时需要连本地假服务器。可以替换域名、放行 http 的构造函数只在 `#[cfg(test)]` 下存在，正式构建里根本没有这段代码。

### 界面隔离（Tauri）
- **token 只存在于 Rust 一侧。** 界面能拿到的只有第 6.3 节的状态快照（账号列表里的本地 ID、通行证 ID、备注、原神角色、凭证状态，以及运行状态、提示文字）和截图目标列表，不包括截到的画面和二维码内容。
- **确认对话框由 Rust 端弹出。** 网页端没有 dialog 权限，网页里的代码没法替你点确认。登录和解绑的确认都这样做（v0.1 里替换已绑定账号的确认，v0.2 起不再需要，第 6.1 节）。
- **能力收到最小：**
  - capabilities 只开放我们自己的命令（通过 app manifest 生成权限）和事件监听，不启用文件、Shell、HTTP、opener 等插件；
  - CSP 只允许本地资源，`img-src` 额外允许 `data:`，用来显示绑定二维码的 SVG；
  - 二维码文本、窗口标题这类外部文本一律用 `textContent` 显示，不用 `innerHTML`。

界面和 Rust 之间的接口（v1）：
- **命令：**
  - `get_state`；
  - `bind_start` / `bind_cancel`；
  - `set_active {id}` / `set_note {id, note}` / `unbind {id}` / `delete_leftovers`（v0.2）；
  - `list_targets`；
  - `scan_start {target}` / `scan_stop`；
  - `update_settings`。
  - 账号相关的命令在扫描中、绑定中一律拒绝。
- **事件：** `state-changed`，内容是完整的状态快照（第 6.3 节）。

### 日志和错误信息
- stoken 用 `secrecy::SecretString` 包装，打印时显示成 `[REDACTED]`。
- stoken 只放在 Cookie 请求头里，不放进 URL；这个请求头标记为敏感（`HeaderValue::set_sensitive`），调试输出里不会显示。
- reqwest 的错误信息会带上完整 URL，所以错误一律先用 `reqwest::Error::without_url()` 去掉 URL。
- 有测试专门检查：错误信息和调试输出里不会出现 token 原文。
- v1 不写日志文件（第 8 节）。以后加日志时，同样不能出现 token、ticket 和二维码内容。

## 10. 错误处理

- **服务器返回什么都不崩溃。** 返回内容一律按定义好的结构解析，字段缺失或格式不对只当作普通错误处理。后台任务里的错误都通过事件传回界面，不会让程序退出。
- **错误分类：**

| 类别 | 例子 | 界面提示 |
|---|---|---|
| 凭证失效 | stoken 过期（retcode `-100`） | 请重新绑定这个账号（只标记这一个账号） |
| 二维码问题 | 已过期（`-3501`）、已被扫、ticket 无效 | 请在游戏里刷新二维码（继续扫描） |
| 应用不符 | scanQRLogin 返回的应用 ID 不是这个游戏 | 已取消登录，显示服务器返回的应用名 |
| 环境问题 | 找不到窗口、窗口最小化、截图失败、断网 | 具体原因和建议 |
| 接口变化 | 未知 retcode、返回格式不对 | 显示 retcode 和服务器返回的 message，提示接口可能已变更，请提 Issue |

- **重试规则：**
  - 只有重复发送也没有副作用的请求（查询绑定状态、检查凭证、查原神角色）才自动重试，最多一次。查原神角色再失败也不提示（第 6.4 节）。
  - 扫码登录的三步失败后都不自动重试。
- **截图失败：** 偶尔一帧失败直接跳过；连续 10 帧失败就停止扫描并提示原因。
- **账号文件读写失败：** 处理规则见第 8 节。

## 14. 需要在 M1 实测确定的事项

2026-10-12 已全部有结论。

1. **接口细节。** 第 6 节的接口事先对照活跃开源项目核对过，但各项目之间有几处不一致。2026-10-12 用真实账号实测，`cli bind` 和 `cli login --image` 都一次成功，原神客户端登录成功。各项结论如下，全部是第 6 节的首选方案：
   - **panda 扫码的域名：** `api-sdk.mihoyo.com` 可用。备选的 `hk4e-sdk.mihoyo.com` 不需要。
   - **DS 签名：** 不需要。`scanQRLogin`、`confirmQRLogin` 不带 DS 也成功了，所以计划里的 DS2 签名（任务 19）没有做。
   - **原神的 passport 应用 ID：** `scanQRLogin` 对 PC 客户端二维码返回的 `data.app_id` 是 `c76ync6mutq8`。程序在确认登录前会核对这个值，不一致就取消登录；这次核对通过了。
   - **检查凭证的接口：** `getCookieAccountInfoBySToken` 在 `passport-api` 域名下可用。
   - **绑定：** HoYoPlay 那套请求头可用。备选的 `x-rpc-app_id: dw9y09jqjpxc` 不需要。
2. **截图后端选 GDI 还是 Windows.Graphics.Capture（WGC，都用 xcap）。** 合格标准是：
   - 本程序以普通权限运行，能截到以管理员权限运行的原神窗口的真实画面，不是黑屏；
   - 不需要管理员权限，也不弹系统授权提示；
   - 在 4K 屏上维持每秒 4 帧，本程序 CPU 占用不超过一个核心的 25%。

   两种后端都合格时选 GDI，因为它不需要额外的 feature。

   实测环境：4K 显示器（3840×2160，缩放 150%）；原神以管理员权限运行，窗口 1922×1126；实验程序（`spikes/capture-bench`）以普通权限运行。每种组合跑 60 秒，目标每秒 4 帧。

   | 后端 | 截法 | 结果 | 平均每帧耗时 | CPU（一个核心） | 是否合格 |
   |---|---|---|---|---|---|
   | GDI | 截窗口（PrintWindow） | 截到的图是 1424×1076，和窗口尺寸对不上；非黑像素占 99.0% | 179.5 ms | 67.6% | 否，CPU 超标 |
   | GDI | 截窗口所在的屏幕区域（BitBlt） | 1922×1126，非黑像素占 99.2% | 14.8 ms | 1.2% | **是** |
   | WGC | 截窗口 | 20 次都超时（`timed out waiting on channel`），一帧也没截到 | — | — | 否 |
   | WGC | 截窗口所在的屏幕区域 | 1922×1126，非黑像素占 99.2% | 35.9 ms | 6.8% | 是 |

   **结论：选 GDI 后端，截游戏窗口所在的屏幕区域。** 不需要 `wgc` feature，也就没有 WGC 的黄色边框问题。

   M2 要注意下面几点：
   - **窗口被挡住时截不到游戏。** 截屏幕区域截的是那块区域实际显示的内容，游戏窗口被别的窗口挡住时，截到的是挡在上面的东西。窗口最小化时要暂停扫描，这在第 6.2 节已有规定。M2 审查时进一步发现，这也会让二维码的来源说错，所以自动模式只在游戏是最前面的窗口时扫描（第 6.2 节）。
   - **坐标单位一致。** 窗口和显示器的坐标、尺寸都是物理像素。在 150% 缩放下实测，窗口是 1922×1126，截到的图也是 1922×1126。
   - **按进程名找窗口要自己查 exe 路径。** xcap 0.9.8 的 `app_name()` 先读 exe 版本信息里的描述，读不到才退回 exe 路径。实测拿到完整路径（`…\Genshin Impact Game\YuanShen.exe`），只是因为 YuanShen.exe 没有版本信息，换个有版本信息的游戏就不成立。所以 M2 用 `QueryFullProcessImageNameW` 查 exe 路径再取文件名；用 `PROCESS_QUERY_LIMITED_INFORMATION` 打开进程，普通权限也能查到管理员进程。
   - **按窗口标题找窗口时要求完全相同。** BetterGI 的窗口标题“更好的原神”里也包含“原神”。
3. **云原神的二维码**（已有结论，不用实测）：它是 passport 网页登录码，v1 不支持，见第 2 节“以后的扩展”。
